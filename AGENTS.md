# AGENTS.md — [Gestionnaire Variantes]
Es tracta d'aplicació backend multiusuari monolítica que permeti a un equip de persones que es dedica a codificar productes afegir a la codificació un codi de declinació que permeti classificar les variants.
S'ha de processar tota una base de dades de codificació i fer un interficie GUI per validacions manuals dels resultats.
## Stack i estructura 
Backend Python amb GUI multiusuari en Windows Server 2019/RDS, sobre la instància existent SQL Server 2017 Express. Base exclusiva del projecte: `VARIANTS_PARKOD`, esquema `dbo`; no esquema personalitzat `variants` ni migració de motor prevista. Disseny net i modern. Codi, configuració tècnica, logs i debug en anglès; GUI i missatges externs en francès.
El fitxer 'docs/Parkod.md' conté el model funcional decidit per la nova base de dades. El diagrama i el diccionari de camps són a 'docs/DATA_MODEL.md' i els arguments a 'docs/DECISIONS.md'. Llegiu-los i distingiu els acords confirmats de les propostes tècniques pendents de validació.
## Ordres 
El programa es podrà executar en mode interactiu i en mode batch (com a tasca planificada windows). 
## Convencions
Disseny net i modern. Estandards de Python a seguir. Estandars de SQL a seguir. La programació, parametrització tècnica, logs i tot els missatges de debug i tècnics serà en llenguatge angles. Les interfícies GUI i els missatges al mon exterior seran en llenguatge Francés. 
- Prioritzeu SQL estàndard quan sigui possible, sense prometre portabilitat ANSI/ISO completa ni substituir mecanismes SQL Server aprovats. Manteniu a SQL integritat, controls compartits de sessió/permisos/reserva, concurrència i atomicitat de dades/auditoria; no els traslladeu a Python per aparent portabilitat. Procediments acotats, transaccions curtes i responsabilitat clara d'errors/COMMIT/ROLLBACK; eviteu SQL dinàmic o complexitat innecessaris.
- Documenteu cada dependència específica de SQL Server, de sintaxi o comportament, amb comentaris en anglès al punt d'ús del codi SQL: característica, motiu i garantia a preservar si se substitueix. Incloeu-hi bloquejos, aïllament, collations, tipus/sintaxi i índexs, no només paraules clau T-SQL. Manteniu l'inventari a `docs/DATA_MODEL.md` §6.12 i els arguments a `docs/DECISIONS.md`. Documentar no aprova noves dependències ni autoritza modificar SQL legacy.
## Regles de domini / trampes conegudes
El programa està fortament lligat amb el mon de la codificació. No tots el requeriments arribaran escrits. Per qualsevol dubte, incoherencia o dada mancant, aturat i pregunta. S'admeten idees per a aconseguir més informació per a poder agrupar les variants amb més certesa.
- El codi Parkod és un SKU de vuit caràcters exactes `A-Z` i `0-9`: `CMARQ(3) + CCATEG(2) + CPROD(3)`. Parkod diferent implica variant diferent, però no necessàriament grup comercial diferent. EAN diferent no implica variant diferent.
- Cada SKU té una única ProductVariant amb codi propi `BIGINT IDENTITY(1,1)` i PK. No genereu identificadors amb `MAX + 1` ni els recicleu en l'operativa normal.
- Es conserven ProductGroup, ProductGroupId i ProductGroupVariantType, no Product/ProductId. ProductGroup té PK `(BrandCode, CategoryCode, ProductGroupId)`: BrandCode NVARCHAR(3) NOT NULL, CategoryCode NVARCHAR(2) NOT NULL, ProductGroupId INT positiu NOT NULL numerat des d'1 per marca–categoria, no per línia. El número es pot repetir fora de la parella i és independent de ProductVariant.ProductCode (CPROD). ProductGroupCounter i `sp_getapplock` per parella estan aprovats, DDL pendent; no IDENTITY global ni MAX+1.
- ProductVariant.LineCode i ProductGroup.LineCode són NVARCHAR(2) NOT NULL. El primer hereta Parkod.CLIGNE del mateix SKU, el segon la línia del primer SKU creador del grup. La font actual informa CLIGNE; marca i categoria també s'hereten. La FK SKU/grup inclou línia; la FK SKU/còpia usa només els tres codis del SKU. No recuperar la FK SKU/còpia de quatre camps amb CLIGNE: SQL Server la comprovaria abans del final de la correcció atòmica. Comproveu igualtat CLIGNE/LineCode als procediments protegits.
- Cada variant té un únic ProductGroup amb la mateixa marca, categoria i línia informada. Compartir aquests codis no basta per decidir la pertinença comercial. Cada SKU no agrupat rep un grup propi; no utilitzeu un grup genèric compartit. Els noms poden repetir-se i els grups buits es conserven. Si CLIGNE canvia a l'origen per un SKU classificat, preserveu còpia/decisions, logueu i deixeu-lo present fins a revisió tècnica; no reclassifiqueu silenciosament.
- Tots els camps textuals nous són NVARCHAR; marca, categoria i línia utilitzen el sufix Code, no Id. No canvieu els tipus ni les dades legacy; aquest acord no amplia CI_AI ni la normalització de blancs a altres camps.
- ProductGroup.PrimaryVariantTypeId és comú per a qualsevol ús. Només compten les associacions ProductGroupVariantType amb IsValidated=1 i ParkodVariantCode no nul: 0 exigeix NULL; 1 aquell ID; més d'1 selecció tècnica. No és un recompte de SKU/valors; s'aplica també a grups d'un sol SKU i buits segons habilitacions conservades. Candidates i aprovades de fase 2 sense codi no alteren principal ni lectura Parkod.
- El principal ha de ser un tipus habilitat al mateix grup i compatible amb BrandCode, no un SKU ni un valor. La mateixa VariantType pot ser principal de diversos grups. No elimineu ni fusioneu altres tipus, valors o SKU per seleccionar-lo, ni escolliu arbitràriament el primer quan n'hi ha diversos.
- Si falta el principal obligatori o no és vàlid, bloquegeu l'exportació i rebutgeu estats finals invàlids, permetent correccions. Revalideu atòmicament habilitacions finals, principal i trasllats; no substituïu decisions tècniques vàlides. NULL amb zero tipus no autoritza exportació. Acords consolidats fins a D228; DDL i proves pendents, sense autorització de desplegament.
- La còpia `VARIANTS_PARKOD.dbo.Parkod` conserva els noms originals dels vuit camps; `CMARQ = ProductVariant.BrandCode`, `CLIGNE = LineCode`, `CCATEG = CategoryCode` i `CPROD = ProductCode`. A la còpia de proves aportada, els noms es consulten directament a `PARKOD.NOM_MARQUE`/`PARKOD.NOM_LIGNE`, sense copiar-los com a columnes addicionals. La taula d'equivalències de `docs/DATA_MODEL.md` §5.3 és només documental, no una taula SQL ni autorització de reanomenar camps interns.
- **No-intervenció absoluta en `parkod`:** aquest projecte no hi executa escriptures de dades, DDL, manteniment, creació d'objectes, índexs, triggers, usuaris ni concessions de permisos, ni canvis de compatibilitat, collation o aïllament. Només lectures controlades i autoritzades, amb impacte verificat; no prometeu impacte nul ni feu servir NOLOCK. Si una solució exigeix modificar l'original, redissenyeu-la. Els permisos de lectura han d'estar disponibles sense intervenció del projecte a la base original.
- Inventari de la còpia de proves (`docs/DATA_MODEL.md` §5, D223–D228): PARKOD per copiar només els vuit camps acordats; NOM_MARQUE/NOM_LIGNE i preus només consultables. CATEGORY (IDCategory, IDFamily, CategoryName), FAMILY (IDFamily, FamilyName) i EAN (IDParkod, EANNum) només en lectura puntual, sense còpia ni FK. Aquestes quatre són les dependències necessàries; BRAND/LINE es conserven amb equivalències documentals, però no són necessàries per als noms ni un fallback automàtic. FAMILY només per navegar/preparar lots marca–família; DEPARTEM exclòs. Nom inicial amb NOM_MARQUE/NOM_LIGNE/CategoryName del SKU creador, mateix ordre/fallback/límit 150, sense copiar denominacions. Cap altra font funcional sense validació.
- La nova parkod aportada és una còpia de producció per a proves, no l'original. No assumir nous noms a producció ni ubicació/instància de la còpia respecte del destí de proves; metadades SQL reals, permisos i claus/unions pendents de contrastar. CSV/XML/scripts preparatoris no proven desplegament ni autoritzen executar càrregues o canviar fonts. IDCountry no filtra, agrupa, identifica ni classifica: producte independent del país; no filtre equivalent CODE_PAYS ni unicitat global presumpta o selecció/fusió arbitrària de files ambigües.
- `IDParkod = BrandCode + CategoryCode + ProductCode = CMARQ + CCATEG + CPROD`; `IDLine = IDBrand + LineCode = BrandCode + LineCode = CMARQ + CLIGNE`. Concatenació textual sense separadors ni conversió numèrica, zeros preservats: 3+2+3=8 i marca–línia informada 3+2=5. IDBrand correspon a BrandCode; IDLine no és LineCode ni IDParkod ProductVariantId. Cap columna nova ni canvi de NOT NULL intern per línies buides del mestre.
- Totes les escriptures, restriccions, procediments, sessions, bloquejos lògics, auditoria i SynchronizationStatus són a `VARIANTS_PARKOD.dbo`. Configuració aprovada només per a la nova base: compatibilitat 140, collation general French_CI_AS, ALLOW_SNAPSHOT_ISOLATION ON i READ_COMMITTED_SNAPSHOT OFF; pendent de crear/provar. `parkod` conserva compatibilitat 100, French_CI_AS i SNAPSHOT OFF. OPENJSON es preveu a la nova base, no a l'original. Les lectures SNAPSHOT no poden incloure indiscriminadament l'original; protocol entre bases, permisos existents, coordinació amb carregador i adaptació del lector pendents abans de tancar etapa 0. Express: 10 GB de dades per base, recursos de servidor compartits.
- Els EAN es poden consultar per identificar variants, però l'app no gestiona ni corregeix EAN, la seva vigència o l'històric. No introduïu taules Gtin, VariantGtin ni ParkodVariantLink.
- Respecteu les unitats comercials del fabricant, sense conversions. Els estructurats poden ser numèrics o textuals: `VariantType.ValueKind NVARCHAR(7) NOT NULL`, numeric/text, declara la representació homogènia per VariantTypeId; `open_type` exigeix text. Exactament un NumericValue/TextValue informat, segons el pare; no rèplica ValueKind ni nova FK. Els números són `DECIMAL(18,3)`, únics per tipus quan no són NULL; no FLOAT, arrodoniment ni preservació de formats equivalents. No deduïu la forma només de Type.

El canvi ordinari queda bloquejat amb qualsevol VariantTypeValue, encara no assignat, o qualsevol ProductGroupVariantType.IsValidated=1 del tipus en qualsevol grup, encara sense codi ni valors. Comprovació/canvi atòmics respecte d'altes de catàleg i aprovacions; no invalidació ni eliminació automàtica ni extensió de D142 a ValueKind. Default/collation específica no aprovats.

ProductGroupVariantType només admet l'associació si `VariantType.BrandCode IS NULL` o coincideix amb `ProductGroup.BrandCode`. Un tipus global utilitzat només per una marca no esdevé exclusiu.
- `open_type` continua exclusivament textual, però no és l'únic Type que pot utilitzar TextValue. A VariantTypeValue, `TextValue` no nul és únic dins del seu `VariantTypeId` després de normalitzar blancs i segons CI_AI, però pot repetir-se entre tipus diferents. Els NULL numèrics queden fora de la unicitat textual i els NULL textuals fora de la numèrica. Diversos SKU poden reutilitzar el mateix VariantTypeValueId; no dupliqueu files del catàleg per representar variants.

Un blanc especial aïllat també es converteix. Feu-ho abans de validar la unicitat i desar, en insercions/edicions interactives i batch; no es desen blancs als extrems ni blancs consecutius. Validesa final = IsValidated=1 i codi no nul; fase 2 permet indicador 1/codi NULL. Immutable, únic per marca–categoria entre actuals/retirats, mai reciclat, tampoc en reactivar parella.
